# 每日流量情報自動發佈：錯誤與學習紀錄

> 記錄 2026-11-02 從「自動發佈失敗」到「Source-First 架構穩定運作」的除錯過程。
> 目的是讓之後維護的人（或 AI）知道每個設計決定的由來，避免重蹈覆轍。

## 目前架構（結論先講）

```
① 真實來源（scripts/news_sources.py）
   Google Trends 熱搜 RSS ＋ 各區主流媒體 RSS
   → 剔除 48 小時以上舊聞、失效連結、與該區無關的報導
   → 各媒體輪流取稿，每區候選約 20~35 則，每則給 cid
② AI 編輯（scripts/collect_traffic_ai.py）
   七區依序送 Gemini（間隔約 62 秒），每區只送 16 則精簡候選
   AI 只能「以 cid 挑稿」＋翻譯＋寫摘要，不能產生網址
   另回傳 6 則備選；失敗區域最後補跑一次；最後做一次全域分析
③ 組裝與審查
   程式以 cid 對回真實網址；同一媒體每區最多 3 則（軟性上限）
   致命錯誤（結構壞掉）才停止；品質問題標註後照常發佈
```

保護機制：Gemini 每日額度用完立即停止、AI 總時間上限 20 分鐘、失敗自動開 Issue 通知。

---

## 錯誤 1：Gemini 模型下架，AI 採集全部失效

- **現象**：11/02 排程失敗。`gemini-2.5-flash`、`2.0-flash`、`1.5-flash` 全部回 HTTP 404。
- **根本原因**：模型名稱寫死在程式裡，Google 下架舊模型後就壞了。
- **修正**：改用 ListModels API 自動探測可用的 flash 模型，並可用 `GEMINI_MODEL` 環境變數覆寫。
- **教訓**：外部服務的版本號不要寫死；要能自動探測，或改設定就能換。

## 錯誤 2：自癒迴圈「換回同一個死連結」

- **現象**：8 輪自癒都卡在同 3 則，log 顯示 `tw.news.yahoo.com -> tw.news.yahoo.com`。
- **根本原因**：替代網址用 `pool[rank % len]` 選，同一個 rank 每一輪都選到同一個。
- **教訓**：重試或替換時一定要「前進」，並排除已經失敗過的選項，否則重試只是在原地打轉。

## 錯誤 3：「100% 合格才發佈」導致整天停擺

- **現象**：70 則裡只要 3 則連結失效，整天就沒有發佈。
- **修正**：審查改成兩級。致命錯誤（結構壞掉）才停止；品質問題標註 `linkUnverified` / `qualityWarnings` 後照常發佈。
- **教訓**：先決定「每天一定要有」還是「每則都完美」。前者需要分級審查，後者要接受停擺。本專案選擇前者。

## 錯誤 4：AI 產生的網址看似合格，其實是舊聞或捏造的

- **現象**：修好模型後，AI 版 70/70 連結都通過，但大量連到 **2024 年的舊文章**或媒體首頁。
- **根本原因**：讓大型語言模型自己產生新聞網址。驗證只能確認「打得開」，沒辦法確認「是今天的、真的」。
- **修正**：改成 **Source-First 架構**。網址只來自 RSS，AI 只能用 cid 挑稿。
- **教訓**：**不要讓 AI 產生事實性的識別碼**（網址、編號、日期）。由程式提供真實資料，AI 只負責挑選和改寫。

## 錯誤 5：「自癒」其實是在騙過審查

- **現象**：舊版遇到失效連結就換成媒體首頁，看不懂的標題就換成「重點關注話題…」這種套話，審查全部通過。
- **教訓**：自動修復不能用「換成能通過檢查的假內容」來修。審查也要能抓出這種假修復，所以現在加了「首頁連結」「重複連結」「外文未翻譯」等檢查。

## 錯誤 6：區域來源不夠聚焦

- **現象**：中國區出現歐洲抗議、F1、NBA；中東區出現烏克蘭、不丹、MLS。
- **根本原因**：BBC 中文、Al Jazeera 是全球新聞的 RSS；中國區借用的香港 Trends 熱搜多半是國際體育。
- **修正**：綜合型來源和熱搜一律加區域關鍵字過濾。中東的阿拉伯文熱搜直接保留；AI prompt 也要求只選與該區直接相關的新聞。
- **教訓**：「用某種語言報導」不等於「跟某個地區有關」。

## 錯誤 7：候選池被單一來源佔滿

- **現象**：中國區 10 則全是中新網，「每家媒體最多 3 則」完全沒發揮作用。
- **根本原因**：媒體候選照 RSS 順序截取前 15 則，中新網三個頻道排最前面，各 8 則就把名額填滿了，SCMP 一則都進不來。
- **修正**：改成各媒體輪流取稿，同一媒體的多個頻道合併計算。
- **教訓**：多元性的限制要在**最上游**（候選池）就落實；只在下游挑選時限制，候選池早已不多元。

## 錯誤 8：硬性上限剔除稿件後，補進不相關的稿

- **現象**：AI 選了 9 則中新網，被剔除 6 則後，程式補位補進未翻譯的國際體育新聞。
- **修正**：AI 另外回傳 6 則已翻譯的備選。遞補順序是 AI 主稿 → AI 備選 → 超過上限的 AI 稿 → 程式補位。
- **教訓**：限制要有「優雅退讓」的順序。寧可同一家媒體多一則，也不要放品質更差的稿件。

## 錯誤 9：免費方案配額，平行送出反而更慢

- **現象**：
  - 一次 70 則的大請求：Gemini 逾時 5 次，跑了 19 分鐘。
  - 改成 7 區平行送：一直被 429 拒絕，跑了 7 分鐘。
  - 改成 3 區平行：仍然 429，跑了 15 分鐘。
- **根本原因**：免費方案的每分鐘請求數和 token 數上限很低。平行送出加上重試會互相干擾，越塞越慢。
- **修正**：依序送出，每個請求間隔約 62 秒；精簡 prompt，token 約減半；失敗區域最後補跑一次。
- **教訓**：遇到配額瓶頸時，**主動排隊比被動重試快**。先算清楚配額，再決定送的速度。

## 錯誤 10：每日額度用完後，重試變成空等

- **現象**：一天內連續實測近 10 次後，每個請求都回 429，程式對 3 個模型逐一等待重試，跑超過 30 分鐘。
- **根本原因**：沒有分辨「每分鐘限流」（等一下就好）和「每日額度用完」（今天都不會好）。
- **修正**：429 是每日額度時，本次執行不再使用該模型，全部用完就立即停止。另設 AI 總時間上限 20 分鐘。
- **教訓**：重試前先判斷錯誤會不會自己恢復；任何重試都要有總時間上限。
  另外，**實測本身也會消耗正式環境的配額**，密集測試要考慮會不會影響當天的正式排程。

## 其他順手修正

- 排程提早到 UTC 18:00（台灣 02:00），預留 GitHub 排程延遲。
- 失敗時自動開 Issue；已有未關閉的失敗 Issue 就在裡面留言，避免連續失敗時開一堆 Issue。可用 `simulate_failure` 手動測試。
- `actions/checkout@v5`、`actions/setup-python@v6`，消除 Node 20 淘汰警告。
- 日本區：NHK RSS 已無資料，改用朝日、毎日、Kyodo。
- 發佈改成 `git push origin HEAD`，在分支上手動觸發測試時不會動到 main。
- `PYTHONUNBUFFERED=1`：log 即時輸出，方便判斷每一步花多久。

## 維護速查

| 想調整 | 位置 |
|---|---|
| 新增或更換新聞來源 | `scripts/news_sources.py` 的 `MEDIA_FEEDS` |
| 區域關鍵字過濾 | `scripts/news_sources.py` 的 `REGION_KEYWORDS`、`TRENDS_FILTER` |
| 同一媒體每區上限 | `scripts/collect_traffic_ai.py` 的 `MAX_PER_OUTLET` |
| 送給 AI 的候選數、摘要長度 | `PROMPT_CANDIDATES`、`PROMPT_SNIPPET` |
| 請求間隔、AI 總時間上限 | `PACE_SECONDS`、`AI_TIME_BUDGET` |
| 指定 Gemini 模型 | Repository secret 或 workflow env 的 `GEMINI_MODEL`（可用逗號分隔多個） |
| 致命／品質審查規則 | `scripts/validate_traffic_urls.py` 的 `audit_standards()` |
